# Lua Interpreter

Lua 5.2 interpreter embedded in an Ra (Raft) cluster. Lua scripts are
generated by an LLM agent at runtime; the interpreter executes them with
host-owned side-effects (reads, writes, state transitions).

## AI Agent Behaviour
- Do not edit repository files or apply patches until the user explicitly
  approves (e.g. "implement", "apply", "change <file>").
- Do not run `make`, `erlc`, `rebar3`, `eunit`, or any build/test/shell
  tooling unless the user explicitly asks for that command in this session.
- Treat `interpreter_parse.erl` as **generated** from
  `interpreter_parse.yrl` — never hand-edit the `.erl`; change the `.yrl`
  only. `make` regenerates it when the user allows builds.
- Do not run any Git commands that change repository state (`mv`, `add`,
  `commit`, `restore`, `reset`, `checkout`, `clean`, etc.) unless the user
  explicitly requests that specific command.
- Questions and design discussion → answer only; no code unless asked.
- If asked to revert agent changes, undo edits in the working tree, not
  `git reset`, unless Git is explicitly requested.
- `deps/`, `ebin/` — managed by `erlang.mk`; do not edit manually.

## Architecture

### Execution model
- The interpreter is an Ra state machine. Only the Ra leader executes Lua
  programs; followers maintain identical compiled state for fast promotion.
- When a `{run, RunId, Source}` command is applied, **every member**
  compiles `Source` in `apply/3` and stores the resulting `program()` in
  state. Compilation is deterministic so the program shape is consistent
  across the cluster even though each member holds distinct Fun heap objects.

### Fun reference constraint
- Erlang Funs are valid BEAM heap objects that can be sent between processes
  and nodes, but they cannot survive a VM restart or recompile. They are
  **session-scoped**, not persistent.
- The Ra log must **never** store Fun references. Only serializable values
  (ordinals, `RunId`, committed write markers) belong in the log.

### Recovery on leader loss
Two approaches under consideration (neither fully implemented):
- **Re-execute with idempotent `exec/4`**: new leader re-runs the program
  from the top; host gates writes by checking the Ra log for already-
  committed effects. Reads are always safe to repeat.
- **Statement ordinal in Ra log**: each `apply/3` records the ordinal of
  the last completed statement; new leader counts N steps into its freshly
  compiled chain to find the resume Fun. Requires additional design for
  branching control flow.

## Build & Test
- `make eunit` — preferred quick-test command.
- After editing `.xrl`/`.yrl`, re-run `make` to regenerate scanner/parser
  (human or CI action, not an agent default).

## Coding Style
- 80-column hard limit on all lines in `src/` and `test/`. Wrap comments
  and long expressions; API reference comments use two lines per item
  (spec line + description line) so each fits.
- 4-space indents, `snake_case` for modules/functions/atoms.
- Use `-spec` and `-type` aliases; document public functions.
- Prefer pattern matching and small, pure helpers; confine side-effects to
  clearly named functions (`exec`, `assign`, etc.).
- No comments unless the *why* is non-obvious; no docstring blocks.

### Naming scope (single-word rule)
- **Do not change:** OTP conventions (`process_test`); Robert Virding names
  in `interpreter_parse.yrl` (`numeric_for`, `generic_for`, `functiondef`,
  `check_functioncall`, `dot_append`, `dot_to_tree`, …); Leex conventions
  in `interpreter_scan.xrl` (`TokenLine`, `TokenCol`, …).
- **In scope:** names we introduced. Prefer one word per function/variable;
  no camelCase or compound snake_case. `IfBody`, `ElseBody`, `ElseIf` kept.

## Testing
- Use `?assertEqual`, `?assertError`, `?debugVal`; avoid inter-test state
  leakage.
- Run `make eunit` before submitting; add Lua fixtures to `priv/` when
  tests depend on them.

## Commits
- Short imperative messages matching history (e.g. `Add exec guard`).
- PRs: summary, problem, key changes, test evidence.
- Keep build outputs out of diffs unless there is a clear reason to commit
  them.
